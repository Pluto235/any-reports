📢 写在最前：¶

L1 聊天助手用法：打开终端 → 输入 prompt → 复制代码。

L2 工具用法：会写自定义 /command、配 CLAUDE.md、装几个 MCP，但仍然以单 session、单任务、串行为主，没有形成 Skill ↔ Agent ↔ Hook 的编排。

L2 vs L3 对照（同一个需求："让 Claude 写完代码自动跑测试"）

层级 实现方式 失效点
L2 在 CLAUDE.md 写："写完代码后请自动运行 pytest" 模型可能忽略；长 CLAUDE.md 后注意力被稀释；不可靠
L3 在 settings.json 配 Stop hook：pytest -q && ruff check . \|\| echo "NOT DONE" harness 强制执行，不依赖模型记忆，100% 触发

同样的"自动跑测试"，L2 是祈祷模型听话，L3 是让 harness 替你执法。这就是分水岭。

L3 Agentic Engineering：Claude Code 真正的设计意图是让你成为一个编排者：用 Commands 定义入口，用 Agents 隔离职责，用 Skills 注入能力，用 Hooks 强制约束行为。

Boris Cherny："The best Claude Code users don't write better prompts — they design better systems."

本手册的目标：用最短篇幅，把你从 L1/L2 推到 L3。读完后你应能：
1. 管理上下文像管理稀缺资源一样精确
2. 设计 Skills像 Anthropic 内部那样分 9 大类
3. 编排工作流让 Command → Agent → Skill 形成自动流水线
4. 写 Hooks让自动化真正确定性发生
5. 跑并行 Claude让多个 instance 同时为你工作

第一章：上下文管理¶

1.1 一切的起点：Context Rot（上下文腐烂）的科学¶

Thariq（Anthropic 工程团队）实测结论：
Claude Code 的 1M 上下文窗口包含系统提示 + 完整对话 + 所有工具调用与输出 + 所有读过的文件。当上下文越长，注意力越分散，老的、不相关的内容会干扰当前任务的判断。

关键数字：1M context 模型在用到 300-400k token（约 30-40%） 时，开始出现明显的智能下降，这是软性阈值（与任务有关），但很可靠。

实战法则¶

用户类型 安全区 警戒区 红线
新手 < 40% 40-60% 该 wrap up > 60% 立刻处理
资深 < 30% 60% 仅简单任务 > 60% 切 session
智力敏感任务 < 30% — 任何时候不超 40%

怎么看占用？ /context 命令实时显示。

场景 选什么 为什么
同一任务，上下文都还有用 Continue 上下文里全是 load-bearing 的，别花成本重建

1.3 反直觉核心：Rewind > Correct¶

Thariq 原话："If I had to pick one habit that signals good context management, it's rewind."

❌ 新手做法（Correcting）¶

> 帮我重构 auth.py
[Claude 给方案 A，有问题]
> 不对，应该考虑 X 情况
[Claude 改方案 B，可能仍带 A 的偏见]

最终 context = 文件读取 + 2 次失败尝试 + 2 次纠正 + 修复方案。失败的尝试在污染未来的判断。

✅ 高手做法（Rewinding）¶

> 帮我重构 auth.py
[Claude 给方案 A，有问题 — 但你看到了 X 是关键]
[双击 Esc 或 /rewind 回到提问之前]
> 帮我重构 auth.py，注意 X 情况，foo 模块不暴露 Y，直接走 B 路线
[Claude 一次到位]

最终 context = 文件读取 + 一条带教训的提示 + 修复方案。

进阶技巧：Summarize from here¶

回退之前先让 Claude 总结："summarize from here" — 它会写一份给未来的自己的交接信，包括"我尝试了什么、为什么失败、应该怎么走"。然后再 rewind，就能在新尝试里复用这些教训。

实战示例：

> summarize from here, I'm about to rewind. Include:
  - what I tried
  - why it failed
  - what I learned
  - what to try next

[Claude 输出]
📌 Handoff to future-me:
- ❌ Tried: 把 `auth.py` 拆成 `auth_core.py` + `auth_oauth.py`，让 `foo` 模块直接 import `_internal_token` 走捷径
- ❌ Why failed: 测试 `test_token_rotation` 在 CI 跑 fail；`foo` 暴露 `_internal_token` 导致一个下游 service 拿到旧 token 不刷新
- 📌 Key finding: `foo` 模块**绝不能**直接持有 token，必须通过 `TokenProvider` 接口拿
- ✅ Next try: 走方案 B —— 保持 auth.py 单文件，仅抽出 `TokenProvider` 协议，让 `foo` 依赖协议而非具体实现

[你双击 Esc 回退到提问之前]

> 帮我重构 auth.py。注意：
  - foo 模块不能持有 _internal_token（上次因此 fail）
  - 改走方案 B：抽 TokenProvider 协议
  - 别动 token rotation 逻辑

这一条 prompt 已经把 5 分钟的失败经验编码进了下一次尝试，新 context 里没有那条死路。

1.4 /compact vs /clear 决策表¶

长 session 怎么减负？
        │
        ├─ 任务还在进行，要保动量 → /compact <hint>
        │   特点：有损、便宜、Claude 决定细节
        │   适合：mid-task、模糊细节可丢
        │   关键：永远带 hint！
        │   例：/compact focus on auth refactor, drop the test debugging noise
        │
        └─ 切到新任务、高风险下一步 → /clear + 自己写 brief
            特点：精确、麻烦、你决定带什么
            适合：new task、高风险关键决策
            例：/clear → "我们在重构 auth middleware，约束是 X，关键文件 A B，
                  排除了方案 Y"

关键洞察：永远不要让 auto-compact 自然触发。模型在 context rot 状态下做的总结质量最差。

1.5 Bad Compact 是怎么发生的（避坑）¶

真实场景：debug 跑了很久，autocompact 触发，Claude 总结成"我们一直在 debug 函数 X"。然后你说"现在去修 bar.ts 里的另一个 warning"——但那个 warning 已经被丢进总结失去了。

预防：
1. 用 /context 监控，到 60% 主动 /compact <hint> 而不是等 auto
2. 切换关注焦点前，先 /compact "to do next: 修 bar.ts 的 warning, 之前发现 ..."
3. 任务变化大就直接 /clear + 重新写 brief

1.6 Subagent = 上下文垃圾回收¶

核心判断："Will I need this tool output again, or just the conclusion?"

主上下文里跑 ❌ 派 Subagent ✅
想读 20 个文件找一个函数 "Spin up a subagent to find the auth function"
想 grep 12 个关键词探索 "Spin off Explore agent, summarize the architecture"
想读另一个 codebase 借鉴写法 "Subagent: read repo X, summarize the auth flow, then I'll implement here"
想根据 git diff 写 docs "Spin off subagent: write docs for the changes in this PR"

Subagent 干完之后，20 个文件读取 + 12 次 grep + 3 条死路 全部留在子上下文，只有最终报告回到主上下文。这就是上下文垃圾回收。

进阶：Skills 有 context: fork 字段，能让特定 skill 自动跑在隔离 subagent 里——结合下文 skill 章节使用。

实战示例：跨 codebase 找一个函数的所有 init 位置

> Spin up a subagent to find where we initialize the OAuth client
  across the codebase. Just return file:line and a one-line
  description of each spot. Don't read more than 30 files.

[主 session 出现 task 卡片：Explore — locate OAuth init]
[5 秒后 subagent 返回报告]

📋 Subagent report:
- src/auth/oauth.ts:42        — primary client init (called from app bootstrap)
- src/jobs/refresh.ts:18      — background token refresher creates a 2nd client
- src/api/middleware.ts:91    — request-scoped client for per-tenant tokens
- tests/fixtures/mock-oauth.ts:7 — test stub
- scripts/migrate-tokens.py:23 — one-off migration helper

> 主上下文净增 ~200 tokens；20 个文件读取 + 12 次 grep 全部留在子上下文里
> 你直接基于这个清单决定怎么改，不用先把 20 个文件刷进主上下文

对比反例（如果不用 subagent）：你会在主 session 里 Read 20 个文件、Grep 十几次，主上下文从 30k 涨到 80k —— 后续每一次模型回答都要在这 80k 里找信号，注意力被稀释，回答变笨。Subagent 把"过程性噪音"全部隔离在子上下文，主上下文只拿到结论。这就是 §1.6 说的"上下文垃圾回收"。

2.1 决策树：什么时候用什么¶

你想要的能力是...

│       位置：.claude/skills/<name>/SKILL.md

2.2 Commands 实战 — 你日常的 workflow 入口¶

Boris 法则："如果一件事一天做超过一次，就把它做成 Command 或 Skill。"

极简模板：.claude/commands/ship.md¶

---
description: Test, simplify, and PR a feature end-to-end
---

Run the full ship workflow on the currently changed files:

1. Run all tests; if any fail, stop and report.
2. Verify the feature end-to-end (browser/curl/etc) — not just type-check.
3. Run /simplify on changed files to remove duplication.
4. Generate a commit message that focuses on the WHY, not the WHAT.
5. Open PR with structured body (Summary + Test plan).

Goal: when I come back, the work is shippable, not just compileable.

调用：/ship。

经典 Boris 模板：构建 /go skill¶

Boris 现在写代码的标准 prompt 是：

Claude do <task>, then /go

/go 这个 skill 自动完成：
1. 端到端测试（bash / browser / Computer Use）
2. 跑 /simplify
3. 开 PR

回来时，你知道代码是 work 的，不只是编译通过。

推荐这些 Command（套路化生产力）¶

  agent/skill needs structured weather data (temperature + unit + city).
  SKIP when: user asks about climate trends or historical data — use

# Weather Fetcher

Fetch current weather from the free Open-Meteo API.

## Usage

1. If the user gave a city name, geocode it first via:
   `https://geocoding-api.open-meteo.com/v1/search?name={city}&count=1`
2. Call:
   `https://api.open-meteo.com/v1/forecast?latitude={lat}&longitude={lon}&current=temperature_2m,relative_humidity_2m,wind_speed_10m`
3. Return a JSON object: `{ city, temperature, unit, humidity, wind_speed }`.
4. Default unit is Celsius. If the user asks for Fahrenheit, add `&temperature_unit=fahrenheit`.

For full parameter list see `reference.md`. For sample call/response see `examples.md`.

## Gotchas

- Open-Meteo is rate-limited to 10k req/day per IP — cache results within a session.
- Geocoding can return multiple matches; always pick `results[0]` and log the chosen `country` so the user can correct it.
- Wind speed unit defaults to km/h, NOT m/s.

法则 1：不要陈述显然¶

## Gotchas

### ❌ Don't use `pd.read_csv` on the trades table
- It's 50GB+. Use `pl.scan_csv` (Polars lazy) instead.
- Even chunked, pandas hits memory issues.

### ❌ Don't auto-add timezone to timestamps
- Market data is in NY time but stored naive. Adding tz_localize('UTC')
  silently shifts everything 5h. Always check trader-meta.json first.

第四章：Hooks — 真正确定性的自动化¶

4.1 核心区别：Hook vs CLAUDE.md¶

属性 CLAUDE.md 指令 Hook
执行方 模型（概率性） Harness（确定性）
可靠性 低 — 模型可能忽略，尤其是长 CLAUDE.md 100% — 事件触发就执行
适合场景 风格偏好、判断指导 强制约束、自动化、外部集成
失败模式 静默忽略 显式报错

判断准则：句子里出现 "每次"、"自动"、"必须"、"绝不" 时——用 Hook，不要写 CLAUDE.md。

反例对照¶

❌ 写在 CLAUDE.md ✅ 用 Hook
"永远不要在 commit 加 Co-Authored-By" settings.json 的 attribution.commit: ""
"每次写完代码都要跑 prettier" PostToolUse hook（matcher: Edit/Write）
"绝不要执行 rm -rf" PreToolUse hook 拦截危险 bash
"必须先跑测试再提交" Stop hook 强制验证

4.2 Boris 实战：5 大典型 Hooks¶

1. SessionStart — 动态加载上下文¶

每次启动 Claude，自动注入当前最新信息：

{
  "hooks": {
    "SessionStart": [{
      "hooks": [{
        "type": "command",
        "command": "echo 'Today is $(date). Active branch: $(git branch --show-current). Last 3 commits:'; git log --oneline -3"
      }]
    }]
  }
}

2. PreToolUse — 拦截危险操作¶

{
  "PreToolUse": [{
    "matcher": "Bash",
    "hooks": [{
      "type": "command",
      "command": "echo \"$CLAUDE_BASH_COMMAND\" | grep -E '(rm -rf /|--no-verify|push --force.*main|DROP DATABASE)' && { echo 'BLOCKED: dangerous command'; exit 1; } || exit 0"
    }]
  }]
}

3. PostToolUse — 自动格式化¶

"Claude generates well-formatted code, the hook handles the last 10% to avoid CI failures."

{
  "PostToolUse": [{
    "matcher": "Edit|Write",
    "hooks": [{
      "type": "command",
      "command": "case \"$CLAUDE_FILE_PATH\" in *.py) ruff format \"$CLAUDE_FILE_PATH\" 2>/dev/null;; *.ts|*.tsx) prettier --write \"$CLAUDE_FILE_PATH\" 2>/dev/null;; esac; true"
    }]
  }]
}

4. Stop — 强制验收¶

每次 Claude 结束 turn，自动跑测试 / lint，没过就让 Claude 继续：

{
  "Stop": [{
    "hooks": [{
      "type": "command",
      "command": "pytest -q && ruff check . && echo OK || echo 'NOT DONE: tests/lint failed, please fix'"
    }]
  }]
}

5. PermissionRequest — 路由到外部审批¶

5.1.1 tmux — 持久化与日常服务器工作的更优解¶

worktree 解决的是"代码隔离"，但解决不了"终端断了任务就死"的问题。这就是 tmux 出场的地方。

来自 [[Claude Code入门指南.md]] 的实践经验：

如果你是在本地轻量用一用，claude 直接开就够了；但只要你开始做远程开发、跑长任务、挂 SSH、晚上让它慢慢干活，tmux 基本就会变成必需品。

它最大的价值不是"炫技"，而是避免下面这种情况：
- 任务跑了 1 小时
- 你合上电脑或者 SSH 断了
- 会话跟着一起没了

更稳定的做法是：先进入 tmux，再在 tmux 里运行 Claude Code。即使终端断开，后台会话还在。

最小命令速查¶

tmux new -s claude        # 新建一个名为 claude 的 session
# 在里面运行：claude

# 离开（任务继续跑）
Ctrl-b 然后按 d           # detach，session 留在后台

# 任意时间回来（哪怕重启过 SSH）
tmux ls                   # 看有哪些 session
tmux attach -t claude     # 重新接上

# 杀掉 session
tmux kill-session -t claude

worktree vs tmux 对比表¶

场景 推荐 原因
多 agent 同时改不同分支代码 worktree 各自独立 git 树，零冲突
单 agent 长跑（训练/数据处理/夜跑） tmux 终端断开任务继续
SSH 远程登录服务器（IHEP / 集群） tmux 必备，否则 disconnect 即死，所有进度归零
一台机器并行 N 个任务 二者结合 tmux 多 window，每个 window 跑一个 worktree

结论：worktree 解决"空间隔离"，tmux 解决"时间持久化"。两者正交，不替代。日常服务器工作（尤其是 SSH 远程）几乎一定要用 tmux；多 agent 并行改代码时叠加 worktree。

一份偏向 CC 使用的 tmux 配置：Pluto235/tmux。最省事的安装方法是把仓库链接发给 Claude Code，让它帮你装。

5.2 /batch — Fan Out 到几十/几百 Worktrees¶

/batch 会先面试你（用 AskUserQuestion 收集需求），然后 fan out 到尽可能多的 worktree agents 并行干。

/batch = 自动帮你开几十个 agent + worktree，同时改一堆文件

适合场景：
- 大型代码迁移（v1 → v2 across 200 files）
- 批量重构（所有 service 加 logging）
- 大规模 codemod
- 多文件统一改名/格式化

每个 worktree agent 独立工作 + 独立提 PR，你只负责最后批量合并。

实战示例：给 12 个 service 统一加结构化日志

> /batch 给所有 services/*.py 加结构化日志（用 structlog），
  每个 service 单独开 PR，不要堆到同一个 PR 里

[Claude 触发 AskUserQuestion 面试你]
  Q1: 默认日志级别？     → INFO
  Q2: 错误也要 stack trace？ → 是
  Q3: 是否替换已有的 print()？ → 是，全部替换

[确认后 fan out]
✓ 扫到 12 个 service：auth.py / billing.py / users.py / ... / webhooks.py
✓ 创建 12 个 worktree：.claude/worktrees/batch-auth, batch-billing, ...
✓ 12 个 agent 并行启动（每个 agent 只看自己那一个文件 + 共享的 logger 配置）

[~3 分钟后]
  ✅ feature/log-auth     → PR #2041 opened
  ✅ feature/log-billing  → PR #2042 opened
  ✅ feature/log-users    → PR #2043 opened
  ... (×12)

> 你只批 PR，不写代码。每个 PR 单独 review、单独合并、单独回滚。

适用判断（什么时候该用 /batch）¶

适合 ✅ 不适合 ❌
单文件改动量 < 100 行 改动跨多个文件且互相依赖
改法高度同质（同一个套路套 N 次） 每个文件需要不同思考
能并行 review（PR 互相不依赖） 必须串行合并（B 依赖 A）
大型 v1→v2 codemod、批量加 logging、批量补 type hint 架构级重构、跨服务协议变更

核心：/batch = "我有 N 个独立的同质小任务" → fan out → N 个独立 PR。它不解决复杂耦合任务，只解决"重复劳动"。

5.5 Ralph Wiggum Loop — 长跑自主开发¶

最激进的并行用法：自主迭代直到完成。

# 启动一个能持续跑的循环，每轮：
# 1. 看 issue tracker
# 2. 选下一个 issue
# 3. 写代码 + 测试
# 4. 开 PR
# 5. 等 review，根据反馈改
# 6. 合并
# 7. 回 step 1

参考实现：shanraisshan/novel-llm-26

🚫👶 这是完全不监督模式，不是新手玩法。

最小可跑示例：把"good first issue"自动消化成 PR

Step 1：在终端启动 loop¶

$ claude
> /loop 30m /process-next-issue

每 30 分钟自动跑一次 /process-next-issue skill，最长持续 7 天（loop 内置上限）。

Step 2：写 .claude/commands/process-next-issue.md¶

---
description: Pick the next "good first issue", implement, open PR
---

Goal: pick ONE good-first-issue, implement it, open a PR. If no issue, exit cleanly.

Steps:
1. Run: `gh issue list --label "good first issue" --state open --assignee "" --limit 1 --json number,title,body`
2. If the result is empty, print "No issues to process" and exit 0. Do nothing else.
3. Otherwise:
   a. `gh issue edit <n> --add-assignee @me` (claim it so other loop iterations skip it)
   b. `git checkout -b fix/issue-<n>` from main
   c. Read the issue body. Read related files (use Explore subagent to find them).
   d. Implement the fix.
   e. Run the full test suite. If anything fails, DO NOT proceed — leave a comment
      "Attempted, blocked by failing test X. Needs human." and exit.
   f. `gh pr create --title "fix: <issue title> (#<n>)" --body "Closes #<n>\n\n<summary>"`
4. Done — exit. Loop will fire again in 30 min.

Step 3：必须配的两个 hook（否则会写出垃圾代码）¶

{
  "Stop": [{
    "hooks": [{ "type": "command",
      "command": "pytest -q && ruff check . || { echo 'NOT DONE: tests/lint failed'; exit 2; }"
    }]
  }],
  "PreToolUse": [{
    "matcher": "Bash",
    "hooks": [{ "type": "command",
      "command": "echo \"$CLAUDE_BASH_COMMAND\" | grep -E '(rm -rf|push --force|DROP|--no-verify)' && exit 1 || exit 0"
    }]
  }]
}
  • Stop hook：每次结束 turn 必须测试和 lint 全绿，否则 harness 让 Claude 继续修。这一条是 Ralph Loop 不变成"自动化垃圾生成器"的命门。
  • PreToolUse hook：拦截危险命令，自主长跑场景里你不在线，必须把护栏写死。

实际效果¶

[10:00] /loop 启动
[10:00] iter 1 → 处理 #142 "Typo in README" → PR #2050 ✅
[10:30] iter 2 → 处理 #156 "Add --version flag" → 测试 fail → 评论 "blocked" 退出
[11:00] iter 3 → 处理 #160 "Update deps" → PR #2051 ✅
[11:30] iter 4 → 没有未认领 issue → exit 0
[12:00] iter 5 → 没有未认领 issue → exit 0
... (你睡觉，它继续每 30 min check)

核心警告：Ralph Loop 是全自主模式。没有 Stop hook 强制测试通过、没有 PreToolUse 拦危险命令，它会写出能编译但不工作的代码、能 merge 但 break prod 的 PR、甚至 rm -rf 你的 repo。这不是夸张，是 Boris 多次强调的事实。配了 hook 再开，没配就别开。

▶ 上下文管理（最重要）
  • 40% 法则：超 40% 智能开始下降，60% 必须处理
  • 五选一：Continue / Rewind / Compact / Clear / Subagent
  • 反直觉：Rewind > Correct（错了就回退，别在错的基础上修）
  • Compact 永远带 hint：/compact focus on auth, drop debug noise

▶ 三大原语
  Command  = 你触发的 workflow（.claude/commands/）
  Skill    = Claude 自动加载的能力（.claude/skills/<name>/）
  Agent    = 隔离上下文执行单元（.claude/agents/）
  Hook     = harness 跑的确定性事件钩子（settings.json）

▶ Skill 9 法则（Thariq）
  1. 不要陈述显然，写让 Claude 跳出默认的内容
  2. Gotchas 章节是最高信噪比内容
  3. Skill 是文件夹（progressive disclosure）
  4. 给目标和约束，不要给步骤
  5. 用 config.json + AskUserQuestion 处理 setup
  6. description 是写给模型的触发器
  7. 用 ${CLAUDE_PLUGIN_DATA} 存数据
  8. 存脚本让 Claude 组合而不是重写
  9. on-demand hooks 在 skill 激活时生效

▶ 反模式（一定避免）
  ❌ 主 session 干所有事 → 用 subagent / 切 session
  ❌ 错了再 prompt 修 → /rewind
  ❌ CLAUDE.md 写硬性约束 → 用 Hook
  ❌ auto-compact 自然触发 → 主动 /compact <hint>
  ❌ 通用 agent 一把梭 → feature-specific agent + skills
  ❌ --dangerously-skip-permissions → auto mode
  ❌ 让 Claude 想象 UI → Chrome 扩展

▶ Boris 写代码标准 prompt
  Claude do <task>, then /go
  其中 /go = 测试 + /simplify + 开 PR

▶ 每天三件事
  1. claude --update（每天有新功能）
  2. 读 CHANGELOG.md
  3. /usage 看预算
